# Adaptive AI 0.15.14 — blokada SQLite podczas treningu

Baza 0564ce8bb7edfb9c02b26c04bfe627906ca064e4. 15.11.2026 o 21:42:10 rozpoczęto przygotowanie izolowanej generacji, a o 21:42:27 zakończono je błędem OperationalError: database is locked. Import Recorder trwał ok. 8 minut, nie 4 h 40 min jak w 0.15.12. Eksport 16.11 zawiera tylko 10 tys. wpisów HTTP, bez stack trace tej awarii, dlatego nie można przypisać jej do konkretnego SQL.

Zidentyfikowane podatności: source fence wykonywał install/commit i osobne BEGIN IMMEDIATE, z timeout 2 s; błąd BUSY child zamieniał się w RuntimeError bez retry; odczyt scratch mógł uznać BUSY za uszkodzenie i skasować kopię; publikacja nie optowała w busy retry. Naprawa: jedna transakcja IMMEDIATE, retry przygotowania (maks. 10 prób/90 s okna retry, pojedyncze SQL timeout może przekroczyć okno), backoff po zamknięciu połączeń, zachowanie checkpointów i źródłowych guardów; kod błędu i trace w wyniku child, maks. pięć prób child w supervisor, retry atomowej publikacji bez ponownego replay. Nie włączamy retry korupcji, nie usuwamy danych, nie wydłużamy siedmiodniowego okna ani nie omijamy warunków publikacji. Przy trwałej blokadzie model zostaje zachowany i trening jest paused, nie fałszywie ukończony.

Walidacja: nowy test pełnego child z realnym BEGIN IMMEDIATE konkurencyjnego procesu/połączenia, blokada zwalniana dopiero po statusie Waiting for SQLite; wymagane 100% + Shadow. Test klasyfikacji natywnego SQLITE_BUSY, korupcji bez retry, ponowienia tego samego job i anulowania. Poprawiony dawny test migracji 7->14 (jedyna porażka pełnej walidacji 0.15.13, 3295 testów).
