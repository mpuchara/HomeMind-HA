# Audit fixes F01/F02 — 2026-09-16

Scope: blocking findings F01/F02 from the 0.14.11 audit at commit `24b272cd38f61ff4be3c7f5db6cabef2135d2b8a`.

## Runtime composition checked

The packaged add-on starts through:

`adaptive_ai/Dockerfile` → `/app/run.sh` → `preference_queue_main.py` → `fast_queue_main` runtime stack.

`preference_queue_main.py` installs Candidate preference metrics after Shadow context and before atomic promotion captures the standard Candidate status function. `fast_queue_main.py` then installs atomic promotion and finally user/custom promotion. This ordering remains unchanged. The fixes modify the existing contracts and do not add another runtime wrapper.

## F01 — authoritative named promotion gates

The base Candidate comparison already recorded `candidate_false_early` and `live_false_early` and used them as an independent promotion safety condition. The preference-aware fast-target comparison subsequently recomputed `promotable` and could omit that veto. The same recomputation could also obscure vetoes contributed by earlier status layers.

Fast power Candidates now expose one authoritative `promotion_gates` map plus `promotion_vetoes` and `promotion_veto_reasons`. Standard `promotable` is true only when every named gate passes.

The gates are:

| Gate | Meaning | Custom promotion |
|---|---|---|
| `data_freshness` | feedback/build revision still matches and Candidate is not dirty | never override |
| `version_configuration` | persisted model is versioned and direct-parent policy configuration still matches | never override |
| `offline_gate` | offline benchmark/gate passed | only explicit offline override |
| `action_coverage` | preference evidence reaches the fast sample and per-action requirements | replaceable by explicit custom evidence rules |
| `quality_regression` | Candidate transition accuracy remains inside the allowed regression | replaceable by explicit custom regression rule |
| `false_early` | Candidate does not exceed Live false-early count by the original margin | never override |
| `corrections` | Teach anchors fit and no new explicit correction exists | never override |
| `timing` | standard fast timing objective remains inside its safety tolerance | replaceable only by the explicit custom-promotion evidence path |
| `preference_evidence` | preference confidence reaches the standard threshold | replaceable only by the explicit custom-promotion evidence path |
| `execution_prerequisites` | qualified persisted model is in a lifecycle state that can enter atomic promotion | never override |

The old count requirement is intentionally not inherited by doing `new_promotable AND old_promotable`. Fast preference evidence owns its current sample/action thresholds. Independent vetoes are reconstructed and named separately.

### False-early boundary

The unchanged historical margin is:

`candidate_false_early <= live_false_early + max(2, ceil(samples * 0.10))`

For 40 samples and `live_false_early=0`, Candidate values `0..4` pass this gate and `5+` fail it.

### Reproduction

1. Parent/Live has 0 false-early events.
2. Candidate has 1000 false-early events.
3. There are 40 future pairs, all directionally correct and balanced ON/OFF.
4. Preference confidence, coverage, regression and timing otherwise pass.
5. `promotion_gates.false_early.passed = false`.
6. `promotion_vetoes` contains the false-early reason.
7. Final standard `promotable = false`.
8. Atomic Promote reads the same composed status and rejects the swap.

## Custom promotion exceptions

Custom promotion is an explicit user decision, but it is not a universal safety bypass.

Allowed replacements:

- user-selected minimum total future samples;
- user-selected minimum samples per binary action;
- user-selected maximum future accuracy regression;
- standard preference/timing evidence gates as part of the explicit custom-evidence path;
- offline gate only when `allow_offline_gate_override=true`.

Not overridable by custom promotion:

- stale/dirty build evidence;
- version/configuration mismatch;
- false-early safety veto;
- unresolved/new explicit corrections or failed Teach anchors;
- missing qualified persisted model / invalid lifecycle state;
- atomic ownership/configuration checks;
- Control qualification.

`evaluate_custom_rules()` reports `standard_overrides` for standard evidence gates actually being bypassed. During the atomic call, the custom wrapper re-evaluates the current named gates and sets `promotable=True` only if every non-overridable gate still passes. This closes the race where a hard veto could otherwise change after the initial custom-rule screen.

## UI and atomic promotion consistency

The Candidate status payload copies the same `promotion_gates` and `promotion_vetoes` used to compute `comparison.promotable`. Candidate details render the veto reason(s). Atomic promotion captures the preference-aware status function in the production composition and therefore consumes the same standard decision rather than reimplementing promotion evidence in a second place.

A regression test composes the actual relevant production layers in order:

`preference metrics → atomic promotion → custom promotion`

and verifies that the UI/status result is blocked by `false_early`, standard atomic Promote rejects the Candidate, and permissive custom rules still cannot bypass that hard veto.

No default evidence, preference-confidence, accuracy, timing or per-action threshold was changed.

## F02 — experiment outcome confirmation

Presence experiments previously used one snapshot for two different jobs:

- context used to predict a useful action;
- background state whose change should invalidate the observation;
- evidence that a pre-emptive power action was actually correct.

Those roles are now explicit and separate in every newly prepared trial:

- `prediction_inputs` may contain broad predictive context, including a corridor sensor;
- `background_dependencies` may invalidate the observation but never confirm success;
- `outcome_sources` is the only manifest allowed to settle a positive presence outcome.

A presence `outcome_source` must be a selected predictor with an explicit HA-backed presence role and an explicit area mapping equal to the target area. For binary sensors the role must come from `device_class=motion|occupancy|presence`; a name-only/template binary helper is not sufficient proof. `person` / `device_tracker` can be used only when their tracker role and same target area are explicitly mapped. Missing target/source area or missing verified role means the positive outcome is unobservable, not guessed.

The old merged `snapshot` remains only as a compatibility/diagnostic view. Outcome attribution never consumes it as proof.

Each trial carries a stable `trial_id`. Probe outcomes are anchored to the actual Executor dispatch boundary with `action_at`, `observation_start`, and `observation_end`. Outcome-source baselines are re-snapshotted at reservation/dispatch so a transition that happened before the action cannot become a later success label. A HA `last_changed` before the observation window is rejected even if the current state is already ON.

`observe()` first builds the complete batch of changed/unavailable dependencies, then classifies the result. Entity iteration order therefore cannot change the reward. A valid local arrival in the same observed batch is handled consistently regardless of whether another predictor changed before or after it in the mapping.

Reference trials remain controls rather than counterfactual comfort labels: later arrival while the reference stayed OFF produces `reward=None` unless an actual comfort-loss outcome is separately defined. Interruption, missing ACK, unavailable context, missing verified outcome source, or timing outside the observation window also remain `reward=None`.

### Example

1. Kitchen light trial is proposed from local PIR plus a hall-motion predictor.
2. Both sensors may appear in `prediction_inputs`, but only the explicitly mapped kitchen PIR appears in `outcome_sources`.
3. Executor dispatches the bounded probe; that moment becomes `action_at` and starts the observation window.
4. Hall motion alone changes `off → on`: the trial ends as context changed with `reward=None`.
5. Kitchen PIR changes `off → on` inside the action-bound window: the probe receives the existing `+0.6` reward.
6. The same kitchen transition timestamped before `action_at` does not confirm the probe.
7. For an interleaved reference/OFF trial, a later kitchen arrival is recorded as unknown rather than as a negative reward.

## Safety and ownership invariants

These changes do not alter the ActionIntent–Executor boundary. `Experiments` still only prepares/reserves trial metadata; only Executor may dispatch physical HA service calls. Shadow and unpromoted Candidates remain non-controlling. Manual correction still terminates an active experiment and starts the existing cooldown. Candidate promotion remains atomic and keeps existing ownership handling.

## Persistence and migration

No database schema migration is required.

- Existing models, settings, labels, Candidate generations, paired history and rollback data are untouched.
- The promotion-gate report is derived at read/evaluation time and does not reinterpret stored vectors or historical evidence.
- `prediction_inputs`, `background_dependencies` and `outcome_sources` are additive fields inside newly persisted experiment trial JSON. `outcome_confirmers` remains only a deprecated compatibility alias for diagnostics.
- Active experiments are already invalidated on process restart because continuous observation is lost; therefore an old active trial without this field is never reinterpreted after an upgrade.
- Prepared trials are in-memory only and disappear on restart.
- Stored feature vectors and schema revisions are not changed or reinterpreted.

## Regression coverage

`tests/test_audit_safety_contracts.py` covers:

- 1000/0 false-early reproduction with 40 otherwise-correct future pairs;
- a correct Candidate passing every named standard gate;
- one failing gate being sufficient to veto promotion and returning its reason;
- exact false-early boundary at 40 samples;
- composition of preference → atomic → custom promotion with identical status/atomic outcome;
- custom promotion being unable to override a hard false-early veto;
- unrelated background motion not rewarding a local presence experiment;
- a selected presence sensor in a different HA area not confirming the target room;
- a selected local presence sensor continuing to confirm the trial.

The tests use deterministic fixtures and temporary/in-memory SQLite. They do not connect to Home Assistant or execute physical experiments.

## Known limitations

F02 deliberately fails closed for positive presence attribution. If the target or candidate source lacks an explicit `area_id`, or a binary predictor has no explicit HA presence `device_class`, it may still contribute predictive context but cannot produce the `+0.6` arrival reward. This can reduce experiment yield on installations with incomplete HA metadata; it avoids inventing room or sensor-role mappings. A future shared perception contract can replace the HA metadata requirement only if it provides equally explicit, auditable sensor-to-zone provenance.

This change does not address the other audit findings (feature missingness, occupancy freshness/multi-person trajectories, replay provenance, episode objective, experiment-to-Candidate knowledge transfer, or diagonal LinUCB correlation handling).
