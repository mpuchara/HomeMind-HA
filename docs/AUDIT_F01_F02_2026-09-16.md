# Audit fixes F01/F02 — 2026-09-16

Scope: two blocking findings from the 0.14.11 audit at commit `24b272cd38f61ff4be3c7f5db6cabef2135d2b8a`.

## Runtime composition checked

The packaged add-on starts through:

`adaptive_ai/Dockerfile` → `/app/run.sh` → `preference_queue_main.py` → `fast_queue_main` runtime stack.

`preference_queue_main.py` deliberately installs Candidate preference metrics after Shadow context and before atomic promotion captures the standard Candidate status function. This ordering remains unchanged. The fix changes the existing preference comparison contract instead of adding another runtime wrapper.

## F01 — false-early promotion veto

The base Candidate comparison already records `candidate_false_early` and `live_false_early` and used them as an independent promotion safety condition. The preference-aware fast-target comparison subsequently recomputed `promotable` and could omit that veto.

The preference comparison now has an explicit `false_early_safety_passed` contract. If an upstream comparison exposes the field, it is authoritative. For older/composed summaries without the field, the gate is derived from the existing immutable counters with the original margin formula:

`candidate_false_early <= live_false_early + max(2, ceil(samples * 0.10))`

No default evidence, confidence, accuracy, timing or per-action threshold was changed.

### Example

1. Live has 0 false-early events.
2. Candidate has 1000 false-early events.
3. Preference evidence is otherwise strong and confidence is above threshold.
4. `false_early_safety_passed = false`.
5. Final `promotable = false`.
6. Atomic promotion therefore cannot consume/promote this Candidate.

## F02 — experiment outcome confirmation

Presence experiments previously used one snapshot for two different jobs:

- background context changes that should abort an observation;
- evidence that a pre-emptive power action was correct.

That allowed a motion sensor from another room, present only in the policy background snapshot, to produce the positive `+0.6` presence reward.

A presence trial now stores a separate additive `outcome_confirmers` manifest. It contains only binary/tracker presence entities that:

- participated in the presence-focused proposal inputs;
- are not the target actuator;
- belong to the target HA area when that target area is known.

Background entities remain in `snapshot` and can still interrupt the observation when they change, but they cannot confirm a successful outcome.

`observe()` evaluates the complete set of changed snapshot entities before classifying the outcome, so result classification no longer depends on dictionary iteration order.

### Example

1. Kitchen light trial is proposed from local PIR/radar context.
2. `outcome_confirmers = [binary_sensor.kitchen_pir]`.
3. Executor dispatches the bounded trial and the light ACK is observed.
4. `binary_sensor.hall_motion` changes `off → on`: the trial ends as `context changed`, reward is unknown (`None`).
5. In another trial, `binary_sensor.kitchen_pir` changes `off → on`: local arrival confirms the decision and the existing `+0.6` reward is retained.

## Safety and ownership invariants

These changes do not alter the ActionIntent–Executor boundary. `Experiments` still only prepares/reserves trial metadata; only Executor may dispatch physical HA service calls. Shadow and unpromoted Candidates remain non-controlling. Manual correction still terminates an active experiment and starts the existing cooldown. Candidate promotion remains atomic and keeps existing ownership handling.

## Persistence and migration

No database schema migration is required.

- Existing models, settings, labels, Candidate generations, paired history and rollback data are untouched.
- `outcome_confirmers` is an additive field inside newly persisted experiment trial JSON.
- Active experiments are already invalidated on process restart because continuous observation is lost; therefore an old active trial without this field is never reinterpreted after an upgrade.
- Prepared trials are in-memory only and disappear on restart.
- Stored feature vectors and schema revisions are not changed or reinterpreted.

## Regression coverage

`tests/test_audit_safety_contracts.py` adds deterministic regressions for:

- a strong preference Candidate that must still fail promotion because of false-early veto;
- explicit false-early contract preservation;
- unrelated background motion not rewarding a local presence experiment;
- a selected presence sensor in a different HA area not confirming the target room;
- a selected local presence sensor continuing to confirm the trial.

The tests use the existing in-memory/tTemporary SQLite and experiment fixtures and do not connect to Home Assistant or execute physical experiments.

## Known limitations

The F02 contract uses HA `area_id` when available. If the target has no area assignment, a selected binary/tracker presence input can still confirm the trial because there is no authoritative room mapping to compare. This preserves compatibility while avoiding an invented mapping. A future shared perception contract should supply explicit sensor-to-zone provenance rather than infer it in `Experiments`.

This change does not address the other audit findings (feature missingness, occupancy freshness/multi-person trajectories, replay provenance, episode objective, experiment-to-Candidate knowledge transfer, or diagonal LinUCB correlation handling).
