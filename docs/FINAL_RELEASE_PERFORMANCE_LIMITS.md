**MEASURED.** Phase-scoped process CPU is 2156.90→2384.84 ms (+227.94 ms) Normal and 491.75→581.66 ms (+89.91 ms) 50/10, with +6 and +62 final complete receipts respectively. These deltas include changed work volume. They are diagnostic observations alongside separate registered CPU measurements. [Phase-scoped raw profiles and storage detail](FINAL_RELEASE_RECEIPT_CPU_PROFILE.md)

**MEASURED cost of observable operations.** In 50/10 the retained native verification and affected validation envelopes average ~0.161 and ~0.093 ms per visited evidence-bearing decision. Nested capture JSON alone averages ~0.089 ms per call. These sites provide a partial implementation cost of roughly 0.34 ms per visited decision before complete encoding, queueing, preparation and storage. In Normal the corresponding values are ~0.214, ~0.307 and ~0.191 ms (~0.71 ms partial subtotal). The outer serialization averages 0.083 ms per 50/10 persisted decision and 0.043 ms per Normal decision, mixing qualified and unqualified rows. Guarded writer connection entry/exit averages ~0.39 ms per 50/10 attempt and ~0.53 ms per Normal attempt. The extra storage probe observes ~0.12 / 0.16 ms per sample and ~0.10 / 0.23 ms per page observation (50/10 / Normal). These costs vary with source size, affected topology, batch mix and database state.

**UNKNOWN.** An isolated marginal cost for a fully qualified receipt or an individual rejected receipt has not been measured. The phase profiles combine missing masks, failed comparisons and successful checks. A missing-mask decision still uses lookup, request, serialization and native persistence, but bypasses complete proof verification. An expired prepared entry incurs comparison and refresh demand in addition to the preparation already spent. Some prepared entries serve many decisions and others serve none. Dividing all writer CPU by qualified count would assign the wrong cost to each case. The subtotal above is measured work in this implementation with probe overhead. An irreducible CPU floor would need controlled equal-batch qualified/missing/expired comparisons across source and contract sizes.

**MEASURED PRACTICAL LIMIT.** The registered 50/10 process CPU budget is about 44.6 ms above its ~297 ms comparator. The observed delta is ~135 ms, leaving ~91 ms to recover in that pair. The failing Normal runs need roughly 33–81 ms recovered at the measured comparator values. Past SQL classification reduced one component from 1.94 to 1.00 µs, but improved 50/10 process CPU by at most 4.56% in its own screen and had mixed Normal effects. Native batching frequency and admission phase are larger contributors than isolated lexical or receipt-universe work. The measured writer increment is comparable to or larger than the CPU allowance in some cases. That comparison mixes diagnostic and acceptance conditions and establishes neither an unavoidable increment nor insufficient CPU on Raspberry Pi. ## 50/10 tail attribution

**MEASURED.** The original unprofiled 50/10 screens preserve only the aggregate p95/p99 and signature, without a per-decision latency timeline. Their original rank-defining decisions and cause remain **UNKNOWN**. The reverted experiment's two breaches (+14.42% p95 and +23.57% p99) stand.

Four new, serial diagnostic arms use the existing `--profile-prepare` on the same frozen retained A and rejected B sources with ABBA order and unchanged 24 × 400 ms workload, configured fanout 16, effective fanout 10. All produce 240 matching original decisions with matching inputs and zero HA calls or event losses. The probe adds material overhead. It produces per-decision monotonic ingress/submit/start/intent/finish spans, thread CPU for the complete inference span and writer/preparation wall and CPU spans. **MEASURED.** The p99 boundary comes from tick zero in all arms. For matched index 6 in A1→B1, submit-to-start is 71.05→73.53 ms, start-to-intent 8.37→6.92 ms, and full inference wall/thread CPU 18.82/11.54→21.61/12.57 ms. A2 p95 boundary instead occurs inside inference, with 19.36 ms start-to-intent and 0.52 ms submit-to-start. This separates two mechanisms even within four runs. All eight proxy boundary spans have zero overlap with preparation and overlap collector writes. At the p99 boundary the collector spans overlap ~24.9–44.9 ms of the event-to-intent interval. The overlapping work alone cannot identify causality. Writer SQLite deferrals are 1/0/0/3 and do not order these tails.

**UNKNOWN.** Wall minus thread CPU includes preemption, GIL and waits, and finish occurs after intent. It cannot isolate per-decision Engine or Context lock wait, SQLite blocking, other runnable workers or external host load. Aggregate probe timings do not join those waits to individual decisions. Guest `perf` could run a task clock, but the unprivileged scheduler tracepoint could not be read. Host CPU/VM scheduling and WAL I/O were not sampled in the original screens. This diagnostic shows dispatch queue delay and in-worker time, with no concurrent preparation in the observed boundaries. It does not recover missing causal data for the original screens. ## Benchmark reliability

**PROVEN.** The benchmark uses sorted index floor((n−1)×p/100). At 240 observations, p95/p99 are ranks 228/237 of 240. At 384 they are ranks 364/380. A single new maximum does not itself become the p99, but moving a sample across the boundary can move the selected rank by one. Each ingress produces a correlated group of 10 or 16 decisions. One slow ingress wave can affect both percentiles. The four diagnostic runs place each proxy p99 boundary in the same first wave, consistent with a transient.

**MEASURED BENCHMARK VARIANCE.** The six registered Normal same-revision pairs include +33.8% CPU/+42.5% p95/+77.7% p99 in one pair and +11.6% p95 in another. A subsequent control set also has two timing breaches and qualification 12→13 on identical code. This variability exceeds the margins for some pairs and obscures small effects. Matching original inputs and decisions prevent confusing fixture order with output changes. The 50/10 diagnostic ABBA timing shows an order-sensitive outcome with substantial probe overhead, so it cannot supply a new acceptance result or a variance estimate for unprofiled 50/10.

**INFERRED.** WSL2 adds host/guest scheduling. Python threads can contend for the GIL. Native SQLite/WAL can add busy waits or filesystem latency. The probes run on a Linux filesystem within WSL, and no matched native-Linux/Windows or Pi run identifies the effect size. A synchronized run queue, native and host trace would be needed to distinguish these effects for individual outliers.

Keep registered results and thresholds unchanged. In the separate diagnostic, randomize order within serialized matched blocks, record affinity, OS/VM/CPU and storage state, sample load and capture thread/worker/native wait timelines. Report raw paired ratios and medians with paired block bootstrap intervals once enough independent blocks exist. Keep run pairs as the outer resampling unit. In within-run diagnostics resample ingress waves rather than independent decisions and report first-wave sensitivity alongside the full workload. With few blocks report all observations and uncertainty explicitly. Use same-revision pairs to estimate false threshold crossings and preserve all comparisons, including failures.
