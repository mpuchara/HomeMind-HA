# Audit F03–F05 / F07 / F18 — durable provenance contract

Date: 2026-09-16
Contract version: `1`
Audited release: `0.14.11`

## Production execution path

The packaged runtime remains:

`Dockerfile -> run.sh -> preference_queue_main.py -> fast_queue_main -> main.py`

`preference_queue_main.prepare_engine_extensions()` first composes the existing runtime
extensions and Candidate lifecycle. `provenance_runtime.install(core)` then installs the
provenance contract **before Engine, EventStream and History workers start**. No new
physical-control path is introduced: `ActionIntent -> Executor` remains the only
autonomous HA service boundary.

The relevant runtime chain is:

`HA state event -> Engine.on_state_changed -> entity_history/context -> Engine.process_agent -> ActionIntent -> Executor.submit -> HA service -> target ACK -> reward/outcome`

Historical rebuild still reads `entity_history`; provenance now controls whether a target
transition is eligible to become an independent behavioural experience.

## Contract v1

### Event

`provenance_events` stores:

- `event_id`
- `contract_version`
- `event_time`
- `received_time`
- `entity_id`
- HA `context.id`
- HA `context.parent_id`
- HA `user_id`
- `source`
- `origin`
- a compact state manifest
- `processed_time` for crash-safe event idempotency

The current core callback receives `event["data"]`, not the websocket envelope UUID. For
that reason the v1 `event_id` is a deterministic SHA-256-derived identifier over entity,
HA event time, HA context identifiers and state. It is stable across retries/restarts.
The HA context IDs themselves are stored without reinterpretation.

### Origin

Origin is evidence, not a guess. Current values include:

- `own_command` — matched to HomeMind's persisted command/context registry;
- `user` — HA explicitly supplied a top-level `user_id`;
- `user_intent` — reserved for an explicitly mapped HomeMind UI/service intent;
- `experiment` — an experiment outcome generated by the experiment subsystem;
- `unknown` — insufficient evidence.

A physical target transition with no `user_id` is **not** promoted to manual behaviour.
It stays `unknown` unless an explicit intent is separately mapped. Old
`entity_history.context_user_id` is not used to manufacture v1 provenance.

### Decision

`provenance_decisions` is keyed by the immutable `ActionIntent.intent_id`, used as
`decision_id`, and stores:

- agent and Candidate generation ID when available;
- trigger `event_id`;
- policy/model version and revision;
- feature-schema version/revision;
- reward version;
- reproducible feature manifest (schema export, sparse feature vector, policy head,
  context/target revisions and selected dependency revisions);
- allowed policy actions;
- selected/final action;
- model Desired before Teaching/experiment replacement;
- Teaching ID and taught Desired when Teaching changed the final action;
- `experiment_id` and `episode_id` when applicable;
- actual dispatch status, reason, time and value;
- `ack_event_id` and ACK time;
- outcome reward, reason and time.

The current production diagonal LinUCB chooser does not expose a true action-selection
propensity. Therefore `action_probability` is nullable and is currently stored as
`NULL`. Confidence, UCB score or action margin are **not** converted into a fictitious
probability.

### Experience

`provenance_experiences` is keyed by an `experience_key`. It records the agent,
decision/event/experiment/episode links, learning source and origin, action, reward,
features and structured metadata.

Standard runtime feedback uses a key derived from the decision/episode and reason.
Experiment settlement uses `experiment:<trial_id>:outcome`. Historical replay is keyed by
the target history row. Duplicate keys cannot create a second learning record.

## Persistent own-command evidence

The old `Engine.command_echoes` and `command_contexts` remain as the fast in-memory
mechanism, but v1 additionally persists:

- command ID and related decision ID;
- target entity/property/value/deadband;
- creation/dispatch/expiry times;
- command origin;
- HA response context IDs and their expiry.

After restart, a state can be matched first by HA context ID/parent ID and then by the
bounded target/value/deadband evidence. A matched own command is archived normally for
chronology but historical rebuild refuses to add it as an independent behavioural
demonstration.

The command evidence window is deliberately bounded; after it expires an unattributed
state is `unknown`, not retroactively assumed to be HomeMind or human.

## Replay and old data

Migration is additive. It creates only new provenance tables/indexes and, for an early v1
draft, additively adds `processed_time` / `command_origin` if missing.

It does **not**:

- rewrite `entity_history`;
- reinterpret old feature vectors;
- alter model/schema vectors;
- fabricate origins for old rows;
- change settings, labels, generation history or rollback snapshots.

Historical rows predating v1 therefore resolve to `origin=unknown` unless a real v1 link
exists. This is intentional.

For a new historical transition whose v1 origin is `own_command`, raw chronology remains
in `entity_history`, but `add_historical_experience()` returns before policy learning.
An auditable `historical_replay_excluded` experience is written instead.

## Idempotency and restart behaviour

Event processing has two phases: insertion and `processed_time`. A retry after a crash
between those phases is processed again; a retry after completed handling is suppressed.
This avoids both premature acknowledgement of an unprocessed event and normal duplicate
learning.

Normal runtime feedback persists the updated model, `rl_feedback` row and provenance
experience key in one SQLite transaction. The same feedback key therefore cannot update
the policy twice after retry/restart.

Experiment outcomes also receive a durable key based on `trial_id`; the existing active
trial lifecycle remains the first guard and the provenance key is the restart/retry guard.
Budgets, cooldowns and F02 observation windows are unchanged.

## Safety boundaries

- Executor is still the only autonomous dispatcher.
- Shadow and non-promoted Candidate generations never dispatch.
- provenance code observes/decorates Executor; it does not issue HA services.
- manual priority and Control qualification are unchanged.
- F01 promotion gates and atomic ownership swap are unchanged.
- F02 outcome-source/area/time-window rules are unchanged.

## Acceptance coverage

`tests/test_provenance_contract.py` covers:

1. legacy history stays `unknown` rather than acquiring fabricated provenance;
2. persisted command/context evidence is still recognised after reopening the database;
3. duplicate event IDs and duplicate experience keys are idempotent;
4. unknown action probability stays `NULL`, while a real supplied probability is stored;
5. an explicit manual experience survives restart;
6. a real Executor decision is linked through dispatch, ACK event and outcome;
7. an own-command ACK cannot be inserted into historical demonstrations;
8. duplicate runtime feedback cannot update the model or feedback table twice;
9. a user correction and its provenance survive restart;
10. a physical no-user event stays `unknown`.

Existing architecture tests continue to verify that only Executor calls HA services.

## Example event flow

1. HA context event `E1` triggers inference.
2. Policy produces model Desired `0`; Teaching may replace final Desired with `1`.
3. immutable ActionIntent `D1` is journalled with feature/schema/model/reward versions.
4. Executor validates `D1`, reserves command evidence and dispatches value `1`.
5. HA reports target state with context `C1`; persistent command evidence classifies event
   `E2` as `own_command` and links it as `D1.ack_event_id`.
6. delayed observation settles the episode and records one outcome/experience for `D1`.
7. Later historical rebuild still sees `E2` in raw chronology but does not learn it again
   as if a person independently demonstrated value `1`.

## Known limits

- Events already stored before contract v1 have no trustworthy event/context provenance
  and intentionally remain `unknown`.
- Home Assistant state payloads do not always identify the actor. No-user changes remain
  ambiguous instead of being guessed as manual or automation.
- The current chooser has no true propensity output, so `action_probability` is nullable.
- The v1 event ID is deterministic because the current runtime discards the outer HA
  websocket event UUID before `Engine.on_state_changed`; context IDs remain the native HA
  identifiers and can still link command responses to state events.
